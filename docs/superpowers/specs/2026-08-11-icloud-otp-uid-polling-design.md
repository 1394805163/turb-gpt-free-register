# iCloud OTP UID 增量轮询设计

## 目标

修复 iCloud Hide My Email 在账号登录测活时“邮件已经送达，但程序持续等待并超时”的问题。方案必须在最多 2 个并发任务下稳定工作，避免频繁重新登录 iCloud，也不能把其他别名的验证码交给当前账号。

## 已确认的根因

- 登录测活一次复用同一条 IMAP 连接约 90 秒，期间没有可靠刷新所选邮箱视图。
- 当前实现依赖服务端 `HEADER` 搜索。iCloud 的已选邮箱视图或 HEADER 索引没有及时出现新邮件时，搜索会持续返回空。
- 现场 4 个账号各收到 3 封 OpenAI OTP 邮件；任务原连接均超时。使用新 IMAP 连接后，4 个账号均能解析出 6 位 OTP，证明凭据、投递和解析器正常。
- 另 1 个任务在 OpenAI authorize 阶段收到 HTTP 403，未进入有效收码阶段，必须继续归类为网络临时错误。
- 注册流程之所以较容易成功，是因为它把总等待拆成 15–30 秒片段；每个片段重新调用取信逻辑，间接刷新了 IMAP 连接。

## 方案选择

采用“UID 增量发现 + 本地别名匹配 + 轻量刷新 + 定期重连”的组合方案。

不单独采用以下方式：

- 只调用 `NOOP`/`SELECT`：仍可能受 iCloud HEADER 搜索索引延迟影响。
- 每轮重新登录 IMAP：连接次数过多，增加 Apple 限频和网络抖动概率。

## 邮件发现流程

1. 每个 OTP 等待任务维护独立状态：最后看到的 UID、UIDVALIDITY、已检查 UID、已使用 Message-ID 和验证码哈希。
2. 首次连接后读取收件箱 UID 列表，仅扫描末尾有限窗口，捕获“邮件比等待器更早到达”的竞态。
3. 后续只处理大于最后 UID 的新增邮件，不再使用服务端 HEADER 搜索作为主要发现方式。
4. 下载候选邮件后，在本地严格检查目标隐藏邮箱是否存在于 `To`、`Delivered-To` 或 `X-Original-To` 等收件人头部。
5. 在匹配目标别名后解析验证码；整个等待任务共享去重状态，不能在 OTP 重发后重新接受已使用验证码。
6. 邮件 Date 允许相对请求时间最多 30 秒的时钟误差。是否为新邮件以 UID、Message-ID 和验证码哈希共同判定，不能只依赖时间。
7. 候选邮件按 UID 从新到旧处理，优先使用最新且未使用的验证码。

## 连接生命周期

- 普通轮询间隔保持 2–3 秒。
- 每轮先执行轻量 `NOOP`；每 10–15 秒重新选择一次 `INBOX`。
- 连续 15–20 秒没有观察到 UID 变化，或发生 IMAP/OSError/超时，关闭旧连接并重建。
- 同一等待任务不进行每轮重连；全流水线并发上限继续为 2，因此同时最多存在 2 条 OTP IMAP 连接。
- 重连后检查 UIDVALIDITY。若发生变化，丢弃旧 UID 基线并重新扫描末尾有限窗口，但仍保留验证码哈希和 Message-ID 去重信息。

## OTP 重发规则

- 首封 OTP 最长等待应覆盖正常投递延迟，不因一次空搜索立即重发。
- 重发前保留当前任务全部去重状态。
- 重发后更新请求时间，但保留 30 秒时间容差，并继续拒绝旧 UID、旧 Message-ID 和已使用验证码。
- 单次登录测活最多重发 1 次，避免 OpenAI 发码限频。
- 总等待上限为 120 秒；超过后返回 `temporary_error`，不标记账号死亡。

## 快速测活与完整测活边界

- 默认入池和日常检查使用现有 Access Token 请求 `accounts/check`，成功后即可视为 Token 可用并进入推送流程，不触发邮箱 OTP。
- “登录测活并刷新 Token”作为独立操作，只在 Token 过期、HTTP 401 或用户明确要求刷新时执行。
- OpenAI authorize HTTP 403/429/5xx 归类为网络或出口临时错误，不进入邮箱超时分类。

## 日志与隐私

日志只记录：

- IMAP 连接/重连次数；
- UID 是否增长、候选邮件数量；
- 是否匹配到目标别名；
- 是否解析到验证码以及验证码长度；
- 最终失败阶段和错误分类。

日志不得输出邮箱主账号密码、完整隐藏邮箱、验证码、Access Token 或管理员密钥。

## 测试要求

自动测试至少覆盖：

1. 初始连接看不到邮件，`NOOP`/重新选择后出现新 UID。
2. 当前连接持续陈旧，定期重连后发现 OTP。
3. 不调用服务端 HEADER 搜索也能发现新增邮件。
4. 两个隐藏邮箱共享收件箱时不会串码。
5. 30 秒时间容差能接受刚生成的邮件，同时旧 UID/Message-ID/验证码仍被拒绝。
6. OTP 重发后不会复用上一封验证码。
7. UIDVALIDITY 改变时安全重建基线。
8. 120 秒超时和 IMAP 网络异常只生成 `temporary_error`。
9. authorize HTTP 403 不进入 OTP 等待。
10. 现有注册、账号测活和 iCloud 邮箱池测试全部通过。

## 验收标准

- 使用已确认会收取 OpenAI 邮件的 iCloud 隐藏邮箱执行一次完整登录测活，邮件到达后程序能在 120 秒内取码。
- 日志能证明新 UID 被发现、别名匹配和 OTP 解析成功，但不包含敏感明文。
- 快速测活不触发邮箱 OTP，并能驱动已配置的 chatgpt2api 推送。
- 实际注册、测活、推送总并发始终不超过 2。

## 范围外事项

- 不修改 OpenAI Sentinel、注册协议和验证码生成逻辑。
- 不把 authorize HTTP 403 伪装成邮箱读取问题。
- 不删除或停用仅因 OTP/网络临时错误而失败的账号或 iCloud 别名。
